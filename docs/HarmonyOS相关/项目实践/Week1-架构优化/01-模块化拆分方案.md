## 一、当前项目模块分析

### 1.1 现有目录结构

```
entry/src/main/ets/
├── accountManager/     # 账户管理模块
├── constants/         # 常量定义
├── entity/            # 数据实体
├── entryability/      # 入口能力
├── enum/              # 枚举定义
├── httpRequest/       # 网络请求（含拦截器）
├── model/             # 数据模型
├── native/            # 原生能力
├── network/           # 网络示例
├── pages/             # 页面
├── router/            # 路由管理
├── utils/             # 工具类
├── viewModel/         # 视图模型
└── views/             # UI组件
```

### 1.2 当前模块边界分析

| 模块 | 职责 | 独立性 | 耦合情况 |
|------|------|--------|----------|
| accountManager | 用户登录/登出状态管理 | 高 | 依赖 model/LoginModel |
| httpRequest | 网络请求封装 + 拦截器 | 高 | 依赖 model/BaseResponse, utils/ErrorHandler |
| router | 页面路由跳转 | 高 | 依赖 accountManager, entity |
| utils | 通用工具方法 | 极高 | 无外部依赖 |
| views | 可复用UI组件 | 极高 | 依赖 model, constants |
| viewModel | 页面业务逻辑 | 中 | 依赖 model, httpRequest |
| model | 数据结构定义 | 极高 | 无外部依赖 |
| entity | 业务实体 | 极高 | 无外部依赖 |
| enum | 枚举定义 | 极高 | 无外部依赖 |
| constants | 应用常量 | 极高 | 无外部依赖 |
| pages | 页面实现 | 低 | 依赖 views, viewModel, router |
| network | 示例代码 | 低 | 依赖 httpRequest |

### 1.3 存在的问题

1. **accountManager 与 model 耦合**：AccountManager 直接引用 LoginModel
2. **httpRequest 模块职责过重**：包含网络请求、拦截器配置、环境管理
3. **router 与 accountManager 紧耦合**：LoginGuard 逻辑分散在 Router 中
4. **缺少统一的模块初始化机制**：各模块初始化顺序不明确

## 二、模块化拆分方案

### 2.1 推荐方案：目录结构拆分 + 模块管理器

**优势**：
- 不需要复杂的签名配置
- 适合当前项目阶段
- 便于逐步演进

### 2.2 目标模块结构

│   └── ModuleManager.ets

## 五、关键设计决策

### 5.1 为什么采用目录结构拆分而非 HSP？

- 当前项目规模适中，不需要动态共享
- HSP 需要额外的签名配置
- 目录拆分可以平滑过渡，后续可升级为 HSP

### 5.2 模块间通信原则

- 上层模块可以依赖下层模块
- 同层模块间不允许直接依赖
- 通过接口/事件进行跨层通信

### 5.3 模块的独立性目标

每个模块应满足：
- **可单独测试**：不依赖其他模块即可验证
- **可单独编译**：模块内修改不影响其他模块
- **明确的公开接口**：仅暴露必要的 API

## 六、后续优化方向

1. **HSP 动态共享包**：当模块被多个 HAP 共用时，升级为 HSP
2. **Native 模块化**：将 native 能力封装为独立模块
3. **插件化架构**：支持运行时动态加载功能模块
